# 4.1 — User Creation, Validation, and Rights Management

> **⚠️ UPDATED 2026-07-25 (stakeholder decision) — no *open* self-registration.** There is no public
> `register` route any more; every account traces back to a staff-issued credential. Three paths:
>
> | Path | Who starts it | Where | Scale |
> |---|---|---|---|
> | **Class cohort join code** (primary) | Adviser creates the class; **students enrol themselves** | `/adviser/cohorts` → public `/join/{code}` | a whole class |
> | **Cohort invitation** (fallback) | Adviser adds a student by name + email, singly or by pasting a list | cohort page → public `/join/invitation/{token}` | a few stragglers |
> | **Cohort manual-add** (fallback) | Adviser adds a student by name + email (single or pasted list) | cohort page → `/join/invitation/{token}` | stragglers |
> | **Direct creation** | Admin (any role) | `/admin/users` | staff / one-offs |
>
> **Cohort enrolment is still gated, not open:** the join code is adviser-issued and expires, can be
> capped at an expected headcount, can be restricted to institutional email domains, and can be
> closed or regenerated instantly; email verification still applies before the account can do
> anything. Rationale for the cohort path: an adviser onboarding 40–50 students should not hand-type
> 50 names and emails, and the students already know their own details.
>
> Joiners receive their role from the cohort, so they skip `/select-role` entirely. All paths funnel
> account creation through `AdminUserService::createApplicant()`. Implemented in
> `App\Shared\Onboarding\*` (`CohortService`, `CohortController`, `JoinController`), gated by
> `CohortPolicy` and `UserPolicy::createApplicant`.

## User Creation
| Field | Type | Required | Notes |
|---|---|---|---|
| Full Name | Text | Yes | |
| Email Address | Email | Yes | Used as login / unique identifier |
| Role | Dropdown | Yes | See role list in `0.2-stakeholders-and-roles.md` |
| Department/Office (if applicable) | Dropdown | Conditional | |
| Account Status | Dropdown | Yes | Pending Validation / Active / Suspended / Deactivated |

## Validation Flow (ASSUMPTION)
1. Self-registration (external users) or Admin-created (internal/staff) account
2. Email verification (confirmation link)
3. For staff/reviewer roles: Admin manually validates and assigns role before activation
4. Activated accounts can log in and access role-appropriate features

## User Classification and Modification of Rights
- Admin can reassign a user's role at any time (e.g., promote Reviewer to Approver)
- Role changes are logged in the audit trail (`4.4-audit-trail-status-tracking.md`)
- Bulk role import for OJT batches — confirmed required by the requester (2026-07-04) and built
  the same day (`docs/HANDOFF.md` Part H): a CSV upload with a validate-then-confirm preview
  step, extending the Part F Admin UI.

## Permission Enforcement
- All module actions (submit, screen, review, endorse, approve, sign, report) must check the
  acting user's role against the capability matrix in `0.2-stakeholders-and-roles.md`
- Unauthorized actions return a clear access-denied response and are logged as an audit event
