# 4.2 — File Management and Automatic File Naming Convention

> **⚠️ UPDATED 2026-07-25 (stakeholder decision) — new naming convention now in force.** Stored
> filenames follow:
> ```
> REC-{MODULE}-{DEPARTMENT}-{CONTROLNO}_{YYYYMMDD}_{FILELABEL}_V{n}.{ext}
> e.g. REC-REQ-COLLEGE-0235_20260722_APPROVALLETTER_V1.pdf
> ```
> | Segment | Meaning | Source |
> |---|---|---|
> | `REC` | Fixed system prefix | constant |
> | `MODULE` | `REQ` (DPREQ) / `NDA` (DPNDA) / `REMIS` | mapped from module prefix |
> | `DEPARTMENT` | `JHS` / `SHS` / `COLLEGE` / `GS`, else a cleaned token, else `NA` | applicant department, normalized |
> | `CONTROLNO` | trailing digits of the tracking/control number (`DPREQ-2026-0235` → `0235`) | record ID |
> | `YYYYMMDD` | upload/generation date | system |
> | `FILELABEL` | standardized label (see `App\Shared\Documents\Support\FileLabel::ALL`) | document type |
> | `_V{n}` | version number, baked into the filename so each version is a distinct file | versioning |
>
> Implemented in `App\Shared\Documents\Support\DocumentNaming` + `FileLabel`, applied by
> `DocumentService` to every stored file. The original client filename is retained in
> `documents.original_filename` for reference only — never used as the stored filename. The
> pre-2026-07-25 pattern below is superseded.

> **2026-07-02:** Standardized `RecordID` to a single `[MODULE]-YYYY-NNNN` shape across all
> three modules, matching the FRS's own tracking-number example (`REC-2026-0001`, FRS §V). The
> previous version's examples used three different ID shapes for the same concept
> (`2026-000045`, `2026-OJT-00312`, `2026-000118`) — none of which matched the one shape the
> source FRS actually specifies. See `CHANGELOG.md`.

## General Naming Pattern
```
[ModulePrefix]_[RecordID]_[DocumentType]_[YYYYMMDD].[ext]
```

| Component | Description |
|---|---|
| ModulePrefix | DPREQ / DPNDA / REMIS |
| RecordID | System-generated unique tracking number, format `[MODULE]-YYYY-NNNN` (4-digit sequence, reset yearly per module — matches REMIS's FRS §V `REC-YYYY-NNNN` shape, extended to DPREQ/DPNDA for consistency) |
| DocumentType | Short code for the document (e.g., ResearchProposal, ConsentForm, SignedNDA) |
| YYYYMMDD | Date of upload or generation |
| ext | Original file extension |

## Examples
```
DPREQ_DPREQ-2026-0045_ResearchProposal_20260702.pdf
DPNDA_DPNDA-2026-0312_SignedNDA_20260702.pdf
REMIS_REC-2026-0001_EthicsClearance_20260702.pdf
```

## File Management Rules
- Version control: re-uploaded documents create a new version, old version retained (not
  overwritten) for audit purposes. Each version is a physically distinct file (the `_V{n}`
  suffix), and reviewers can view **any two versions side-by-side** via the Document Version
  History page's "Compare selected" action (stakeholder-additional-features.md, 2026-07-25).
- Max file size and accepted types are defined per document (see `1.3`, `2.1`, `3.1`)
- All files are virus-scanned on upload (ASSUMPTION — confirm IT security requirement)
- Deletion is soft-delete only (retained for audit trail, hidden from normal view) — no hard
  delete by non-admin users

## Archival and Retention (implemented 2026-07-25)

- **Automatic archival on clearance issuance.** When a track's clearance issues, every *superseded*
  version attached to that track's records is stamped `documents.archived_at`. The current
  (approved) version is never touched, and archived versions stay downloadable for audit — this is
  a visibility/lifecycle flag, not a deletion. Implemented in
  `App\Shared\Documents\Services\RetentionService::archiveForIssuedClearance()`, called from
  `ClearanceService` for each track independently.
- **Retention schedule** (confirmed 2026-07-07, Part K; configurable in `config/retention.php`):

  | Record state | Retention | Counted from |
  |---|---|---|
  | Clearance issued | **7 years** | the certificate's own issue date (per track) |
  | Rejected / disapproved / inactive | **3 years** | the terminal transition |

  Aligned with the Philippine Data Privacy Act (RA 10173) and general academic record retention.
- **Disposal is deliberate, never automatic.** `php artisan edms:apply-retention` runs monthly on
  the scheduler in **report-only** mode. Actual disposal needs *both* `--purge` **and**
  `RETENTION_PURGE_ENABLED=true`; one alone deletes nothing. Even when purging, only archived
  **files** are removed — the `Document` rows are soft-deleted and the application record and audit
  trail are retained, so there is a permanent record that disposal happened. RA 10173 requires
  disposing of the personal data, not erasing the evidence that it was processed and disposed.
